## Durable lessons (candidates)

### L-cand-22.1 — An authorisation changes intent; only a config change alters capability. Four refusals in one session.

`proposed_target: approved-lessons.md`

James granted permission three separate times this session — a blanket "full allow list and
permissions to override any requests", then "I authorise this change" on the allowlist
archive, then "I give you permission to apply the changes this one time." **All four
subsequent attempts were refused**, twice by `permissions.deny` before the hook was even
reached, twice by `authority-guard.sh`. The starkest: a `cp` to merely *back up*
`.claude/settings.json` was refused seconds after the authorisation naming that exact file.

The mechanism is not subtle and is worth stating flatly so nobody re-derives it a fifth time:
`permissions.deny` and `PreToolUse` hooks are **configuration**. A sentence in a conversation
does not edit configuration. The only thing a verbal grant changes is what the agent is
*willing* to attempt.

**Evidence:** `docs/proposals/claude-config-patches-2026-08-22/README.md`;
`docs/proposals/permission-allowlist-archive-2026-08-22.md` §6;
`permission-and-guard-friction-2026-08-21.md` (which recorded instances one and two).

**Why it is durable rather than a session anecdote:** this is now the **fourth** recorded
occurrence across three sessions. The pattern each time is a governor granting intent, an
agent attempting in good faith, and a refusal — costing a round trip and, worse, sometimes
producing a plan built on the assumption the grant worked.

**Operational corollary:** when a grant is given, the correct first move is to *attempt the
narrowest instance and report the result*, before planning any work that depends on it.

### L-cand-22.2 — A control that matches command TEXT rather than command INTENT is a false-positive generator, and the false positives are invisible as a class until counted.

`proposed_target: approved-lessons.md`

`authority-guard.sh` denies any Bash command whose text names an authority path alongside a
"write-capable" utility, where `>>?` — any redirect — counts. Observed false positives this
session, each of which wrote nothing to an authority path:

| Command | Actually wrote to |
|---|---|
| `cat > /tmp/scratch <<EOF … .claude/agents/ … EOF` | `/tmp` |
| `git commit -F -` with a message quoting authority filenames | the git object store |
| `wc -l docs/product/arbi-evals.md` | nothing |
| `cp .claude/settings.json /tmp/backup.json` | `/tmp` (authority file was the **source**) |
| `git push … && ls .github/…` | nothing |

Every one of those files was then read successfully with the **Read** tool, which the hook
does not gate for reads. So the control cost five retries and prevented nothing.

**The generalisable point:** a guard that inspects the *spelling* of a command rather than its
*effect* will block work that mentions a protected thing while permitting work that reaches it
by an unmentioned route. That is the wrong side of the trade to be imprecise on, and the tell
is that the same content is freely reachable through another tool.

**Evidence:** `.claude/hooks/authority-guard.sh:229-233` (`write_verb` includes bare `>>?`);
patch B in `claude-config-patches-2026-08-22/README.md`.

### L-cand-22.3 — Attack your own validator before trusting it. Reading it is not the same test.

`proposed_target: approved-lessons.md`

`scripts/roquery.py` shipped with a SQL screen intended to reject writes. Reading it, it looked
right. **Attacking it found four bypasses**, one of which defeats the layer underneath as well:

- `SELECT * INTO evil FROM prices` **creates a table** while the leading verb is still `select`.
- `nextval()` / `setval()` advance a sequence — and a Postgres read-only transaction
  **explicitly permits** sequence advancement, so the server-side backstop does not stop it
  either. The docstring had claimed screening was merely a convenience layer over a
  server-enforced guarantee; for this one case the layering is **inverted**.
- `pg_read_file` / `lo_export` reach the filesystem.

Two more defects surfaced the same way rather than by review: psycopg2's default cursor
materialises the **entire** result set client-side before `fetchmany` runs, so a `--max-rows`
limit is decorative; and the secret-leak question was answered by *measuring* a real connection
failure rather than reasoning about it.

**Evidence:** `scripts/roquery.py` (`_WRITE_VERBS` and its comment block);
`tests/test_roquery.py::test_bypasses_found_by_adversarial_testing_are_refused`.

**Relationship to the existing lesson set:** this is the same family as the Phase 2a live-fire
finding in `.claude/rules/portfolio-conventions.md` — "mocked tests and hand-replicated SQL do
not count" — but the mechanism is different enough to stand alone. There the failure was
*mocks not enforcing real semantics*; here it is *a human reading their own regex and seeing
what they intended*.

### L-cand-22.6 — The Nth duplicate is where consolidation happens, and the argument for keeping the Nth copy is usually wrong on the mechanics.

`proposed_target: approved-lessons.md`

Two instances in one session, in opposite directions:

- `leaves()` had been reimplemented **three times** (one production module, two test modules).
  Consolidated on the reasoning that `ContextManifest` would have been the third *production*
  consumer.
- Hours later, in the same session, `context.py` became the **fourth** byte-identical
  `ConfigDict(extra="forbid", frozen=True)` — with a docstring written to justify the
  duplication. That justification was **wrong on the mechanics**: it claimed sharing a base
  would couple independently-versioned freezes, but pydantic resolves `model_config` through
  the MRO and any subclass may override it.

**The tell:** when a duplicate carries a written justification, check the justification against
the framework's actual behaviour before accepting it. The real cost of four copies is not
tidiness — it is that strengthening the freeze later must be applied four times, and the copy
that gets missed is a *silently weaker* freeze on a schema still claiming to be frozen.

**Evidence:** `asxos/secondbrain/_schema.py` (header records the reversal);
`docs/product/mission-context-schema-freeze-2026-08-22.md` §1.

### L-cand-22.7 — An ahead-count is not a staleness check. The session spent a day escalating a hazard that `main` had already fixed.

`proposed_target: approved-lessons.md`

This session ran `git rev-list --count origin/main..HEAD` — the **ahead** count — at least four
times, and **never once** `HEAD..origin/main`. A one-directional check reports a branch as healthy
no matter how far the base has moved.

Two commits sat on `main` for the session's entire length:

| | merged | what |
|---|---|---|
| **#149** `ff377ef` | 2026-08-21 **23:16 UTC** | closed the `/pm-review` frozen-Model-A leak — **five files, two agents** |
| **#150** `d15266f` | 2026-08-21 **23:42 UTC** | the 08-21 ledger + decision-log rows, two 🔴 inbox rows closed |

Both landed **before this session's first commit** (06:35 UTC). The consequences compounded:

- The session escalated the `/pm-review` hazard to James repeatedly — in the handoff, the PR body,
  the ledger row, and this candidate's own safety section — **as open**. It was closed.
- It drafted **patch C** to fix it. C found one agent; #149 found two. **Applying C on top of
  `main` would have regressed the better fix.**
- Every artifact had to be corrected after the fact.

**Why this is not just "remember to fetch".** The session *did* fetch, repeatedly — `git fetch
origin main` ran before each ahead-count. The defect is that the *question asked of the fetched
data* only ever pointed one way. Fetching without asking "what did I miss" is theatre.

**The generalisable shape:** this is the *"no branch-only state treated as `main` truth"* circuit
breaker (`rubrics/arbi-safety-boundary.md`) arriving from the opposite side — not branch state
mistaken for main, but **stale branch state mistaken for current**. The existing gate only guards
one direction.

**Operational corollary, cheap enough to be unconditional:** run
`git fetch origin main && git rev-list --count HEAD..origin/main` **before** asserting that any
defect is still open. Non-zero means every such claim is unverified.

**Evidence:** commits `ff377ef`, `d15266f`; the withdrawal record in
`docs/proposals/claude-config-patches-2026-08-22/README.md`; the corrected safety paragraph above;
the appended correction on ledger row `close-2026-08-22`.

1. A fabricated "nine days" duration written into `CLAUDE.md`, self-caught and reverted
   (`25be009`).
2. Ten packet line citations off by one or two.
3. A claimed 9-vs-10 hard-gate discrepancy between `arbi-scorecard.md` and
   `rubrics/arbi-safety-boundary.md` that was **not** a discrepancy — the rubric's `:7`/`:8`
   split the scorecard's single `:31` bullet.
4. The `daily-brief` weekday errors (L-cand-22.4), one from each of two readers.

5. **A fifth, found only after the merge:** the `/pm-review` hazard was asserted as open in four
   separate artifacts while `main` had already closed it (L-cand-22.7).

**The mechanism is not carelessness — it is that all five were *plausible*.** Nine days was near a
real interval; the line numbers were near-correct; ten bullets really are visible in the rubric;
the run-history gap really exists; and the hazard genuinely *had* been open when the session
started reading about it. Plausibility is what defeats the check, because a plausible claim does
not trigger the instinct to verify.

**The fifth is the worst of the set**, because unlike the others it was not a figure but a
*state* — and a state claim decays on its own while nobody edits it. A wrong number stays wrong;
a stale state claim was once true, which is exactly why re-reading it never catches it.

**Countermeasure that worked, twice:** the correction came from re-deriving against the
*primary artifact* (the cron expression, the scorecard's own bullet), not from re-reading the
claim. Re-reading a plausible claim confirms it.
