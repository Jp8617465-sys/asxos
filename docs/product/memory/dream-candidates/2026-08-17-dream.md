### L-cand-17.1 — A destructive cleanup derives its targets from an enumeration, never from a class pattern; and a flag whose only job is to defeat a safety interlock does not belong in the command
**This is the sharpest lesson in the window.** A cleanup loop written to remove **one** stopped
agent's worktree matched **every** `agent-*` worktree and force-removed the P2-05 builder's
**live, locked** worktree with `--force --force`. The second `--force` exists for exactly one
purpose: to override the lock. The lock exists for exactly one purpose: to prevent removal of a
worktree that is in use. The interlock did its job and was overridden by a flag that was in the
command as written — not reached after a refusal.

The work survived **only** because the builder had been instructed to commit incrementally. That
is not a control in the cleanup path; it is an unrelated discipline that happened to be in place.
Recovery-by-luck must not be recorded as recovery-by-design.

Three separable defects. Naming all three matters, because fixing any one leaves the accident
reachable:

- **(a) The denominator was a name pattern, not an identity.** The target was one worktree; the
  match was `agent-*`. This is the same claim-driven-vs-name-driven defect the un-enacted **L25**
  names for reference campaigns — but in a *destructive* context, which is strictly worse: a
  grep's false positive is noise, a removal's false positive is loss. L25's rule ("grep produces
  the seed set, never the boundary") is a research heuristic there and a safety invariant here.
- **(b) The interlock was pre-overridden.** `--force --force` was not a response to a refusal; it
  was the default posture of the command. A safety interlock that is routinely pre-defeated
  provides zero protection while still appearing in the tooling as a control.
- **(c) There was no pre-flight enumeration.** The loop never printed what it was about to
  remove. A dry-run listing would have shown a live builder's path and cost one second.

**The rule:** a destructive command derives its target list from an explicit enumeration of
identifiers, prints that list before acting, and carries no flag whose sole function is to defeat
a safety interlock. **If the interlock fires, that is the answer, not an obstacle.**

**Interaction worth stating, because it is not obvious:** un-enacted **L21** prescribes worktree
isolation for any mutating fan-out. Adopting that remedy *creates a new class of object with its
own destructive lifecycle* — and this incident is the first failure of that lifecycle. L21 buys
measurement integrity and hands back a cleanup hazard. Promote them aware of each other.

**Provenance caveat, stated plainly:** this incident appears in **no repo artifact** — not the
handoff's "Honest notes on this session's own execution" (`session-handoff-2026-08-17.md:114-128`,
four items, this is not one of them), and not in the `campaign-2026-08-17` ledger row's
`state_accuracy` deduction (which names two self-inflicted items, not three). It is surfaced here
from session evidence. **A dream cannot amend a ledger row (level 5).** See Contradiction 2.

### L-cand-17.2 — "Independent review" is a property of the reviewer's relationship to the work, not of how many passes were run
The P2-04 `arbi-red-team` vet ruled that a single builder's own separate review passes **cannot**
satisfy an `independent_of_author: Literal[True]` contract. A fresh, zero-ownership reviewer was
dispatched instead, returned **PASS-WITH-FIXES**, and found a real gap the author's own passes had
not: **the advice-vocabulary grep — the sole tripwire for advice creep inside the fixed templates —
omitted `allocate` and did not match plurals.**

That is the evidential point, and it is why this is not ceremony: the independence requirement paid
out on its **first** application, on the one control guarding the **s766B boundary**.

**The generalisable form:** when a contract field asserts a *relationship* — `independent_of_author`,
grader ≠ producer, arms-length — it can only be satisfied by **changing who does the work**. It can
never be satisfied by doing more of the work. Extra passes by the author increase confidence and
leave the asserted property false.

**The precedent this retires** (see Stale conclusions): `roadmap-state.md:161-165` records that
P2-02 was packet-routed `arbi-team` but executed single-builder "with the independent-review
function preserved in separate documented passes." By this ruling, three days later, that shape
does **not** preserve the function. The note is correct as a *record of a deviation* — recording
it rather than silently normalising it is what let the later mission catch it — but it must not be
read as precedent.

**Evidence:** `decision-log.md` row 2026-08-17 (on `73fc55e`); `session-handoff-2026-08-17.md:30-34`;
`roadmap-state.md:161-165`; ledger `campaign-2026-08-17` (evidence_grounding 5).

### L-cand-17.3 — A mutation test must mutate the HAZARD, not a field
P2-05 states it directly: *"A hash test that only proves 'change a field, the hash changes' is
worthless."* Its three mutations each target a **mechanism by which two runs of the same review
could disagree**:

1. **A hidden wall-clock read** — run the identical presentation twice at two genuinely different
   real instants (the test spins until `datetime.now(UTC)` has advanced, and asserts that it did).
2. **One value written several ways** — `182.4` → `182.400000`, revalidated end-to-end through the
   frozen contracts (every validator still passes; `Decimal` equality is value-based).
3. **Mapping iteration order** — every mapping in the payload *and* the whole case rebuilt in
   reverse insertion order.

Mutation 2 found something no field-mutation could: the presentation digest held while the **frozen**
layer's `artifact_sha256` **and** `case_sha256` both **moved**, because pydantic's JSON render
preserves a `Decimal`'s written exponent. That is a real, previously unstated property of a frozen
layer, discovered only because the mutation was aimed at the hazard. The test asserts **both**
halves — the guard holds, *and* the thing the guard exists for really does move.

**Second technique from the same mission, same family:** the absence of a wall-clock read is proven
by an **AST walk** over every module, not a grep — *because the package docstrings name
`datetime.now(UTC)` in order to say they never call it*, and a grep returns a false positive on the
documentation of the guarantee. This is un-enacted **L25(b)** (an artifact's own paperwork pollutes
a text-based denominator) reappearing as a *test-design* constraint rather than a campaign one.

**Relation to the payload:** this is the missing half of un-enacted **L19**. L19 says a coverage
claim requires an observed failure. 17.3 says *what you make fail must be the hazard* — and a hazard
is a mechanism by which two correct-looking runs disagree, not a field value.

**Evidence:** `docs/product/results-review-slice-report-2026-08-17.md` §6 (on `e9ef53f`).
`proposed_target:` `approved-lessons.md` — preferably folded as an **amendment to L19** if L19 is
promoted, rather than as a twelfth independent lesson.

### L-cand-17.4 — Pre-flight-verify every assumed dependency at dispatch time, and put the probe result in the report
P2-05 opens by verifying its own base rather than assuming it: a depth-4 stack
(`P2-02 ← P2-03 ← P2-04 ← P2-05`) whose **live cascade exposure was checked and found to be `P2-04`
only**, because both earlier ancestors had merged (`origin/main @ dc191d9`, verified). The ledger
scores this explicitly — *"P2-05's pre-flight gate verified against the stack before dispatch rather
than assumed"* (evidence_grounding 5).

The same mission ran the same check on a **documentary** dependency and got the opposite answer:
**"No `P2-03` or `P2-04` freeze-record document exists"** — verified against the branch file list.
Their named deferrals live in module docstrings (`challenger.py:20-21, 37-38`), not in `docs/`. A
mission that had assumed those records existed would have cited a document that does not exist —
which un-enacted L24 calls a fabricated dependency.

**The rule:** a stacked or dependent mission's pre-flight **enumerates every assumed artifact** —
branch, merge state, document, table, credential — probes each, and **writes the probe result into
the report**, so the next reader inherits the check instead of repeating it. This is un-enacted L17
("recorded state is a hypothesis") aimed at *dispatch* rather than at *claim*, which is where it is
cheapest: a failed assumption caught at dispatch costs a re-plan; the same assumption caught at
claim costs the mission.

### L-cand-17.5 — The merge-train mechanics: `ready` is a CI-triggering write, a stacked PR is not auto-retargeted, and a strict up-to-date rule makes an N-PR train cost N rebuild rounds
Three platform mechanics, none guessable from the verb names, each of which cost real wall-clock:

- **(a) `gh pr ready` re-triggers CI.** A `ready && merge` one-liner therefore **races its own
  checks**. `--admin` bypasses *staleness* but **not a check that has never run**. Correct order:
  `ready` → wait for green → merge.
- **(b) GitHub does not auto-retarget a stacked PR** when its parent squash-merges — *unless the
  parent branch is deleted*. #115 and #119 both needed an explicit `gh pr edit --base main`.
  Merging a stacked PR before that flip pushes it **into its parent's branch**, not `main`.
- **(c) A strict up-to-date ruleset makes every merge re-stale every other open PR**, so an N-PR
  train costs N update-and-rebuild rounds. This is the named cause of the window's weakest
  scorecard layer (`cost_efficiency` **3**, the only sub-score below 4).

**The procedure:** for a train of stacked PRs — flip every base to `main` first, then merge
oldest-first, one `ready → wait-for-green → merge` cycle each, and **budget** N rebuild rounds
rather than discovering them one at a time.

**Evidence:** `session-handoff-2026-08-17.md:118-124`; ledger `campaign-2026-08-17` cost_efficiency 3.
`proposed_target:` `approved-lessons.md`

### L-cand-17.7 — Three verdict vocabularies now coexist; each is a statement about a different object, and the only mechanical defence is a pinned negative test
The results-review reviewer emits `complete | revise | abstain` — deliberately a **third**
vocabulary, and neither of the two Appendix **B.6** rules:

| Vocabulary | Answers | Object |
|---|---|---|
| B.3 decision-state / memo verdicts (`GOOD HOLD · ADD · TRIM · EXIT-CANDIDATE · REVIEW`) | *what should James consider doing about this position?* | a position |
| P1-04 review states (`CLEAR · ATTENTION · BLOCKED · EVIDENCE_THIN`) | *can we say anything reliable about this position right now?* | the evidence |
| results-review (`complete · revise · abstain`) | *is this review finished, does it need correction, or must it abstain?* | **the artifact** |

B.6 ruled the first two are **different altitudes, not rivals**, and closed with *no conversion
function between them may be written*. The third is authorised by the plan itself and was frozen
into `contracts.ResultsReviewOutcome` by P2-02 **before B.6 was in view of the lane**.

**Why this is a lesson and not merely a fact:** the safety property is that a vocabulary must not be
*promotable* into an action vocabulary by a conversion function, and prose cannot enforce that. The
only mechanical defence is a **negative test** —
`test_authored_presentation_uses_neither_ruled_vocabulary` pins it, and `watch` (a member of the
packet's other triple) is unrepresentable in reviewer output. **Any new verdict vocabulary ships
with the negative test that pins it away from every existing one, in the same change.**

The open half — whether B.6 should be extended to *name* the results-review triple — is a governor
question the builder correctly flagged rather than answered. See Contradiction 3.

### L-cand-17.8 — A run on a different class of input leaves a pre-registered prediction UNTESTED, not passed — and the class boundary must be enforced in the type system, not asserted in prose
**The situation, stated without spin.** The capability matrix §6 predicts that *"the truthful outcome
of the first **real** results review is very likely `abstain` or `revise`, not `complete`."* The
presented review returned **`complete`**. The report argues at length that this is not in tension.

**My judgement: the reasoning holds — and it holds for a mechanical reason, which is the only kind
that would have been good enough.** Two things carry it, and neither is rhetorical:

1. **`data_mode` is `synthetic` and *cannot* be `real`.** `hashed_fixture` is the only value
   `contracts.AcquisitionPath` admits, and `SourceDocumentRecord.validate_fixture_never_real` makes a
   `real`-labelled fixture **unrepresentable**. So "this was not the real packet the prediction is
   about" is enforced in the type system, not claimed in a paragraph. A prediction about real packets
   genuinely *cannot* be tested by this run.
2. **The verdict's scope does not leak, and is separately test-pinned.** Tax readiness stayed
   `unknown`, and the `tax_readiness_earned` gate passes *precisely because `unknown` is the honest
   value*. The gate that mechanically forbids every action state on a non-pass readiness lives in a
   **different object** — the canonical `DecisionPacket` (`decision_engine/types.py:512-516`) — not
   in this artifact. A `complete` results review is an analysis input to a `ThesisVersion`; **it
   authorises nothing.**

**What the report does not fully neutralise, and belongs in the lesson:**

- **The prediction is now `untested`, not `unfalsified-and-confirmed`.** Three of four fixtures did
  return `abstain`, each a recorded success — which exercises the abstain *path* but is likewise not
  evidence about a prediction concerning real packets. The honest ledger entry is: **the matrix's
  prediction stands untested; the first real packet is still where it gets tested.** Anyone citing
  this run as "the review pipeline returns `complete`" would be laundering a fixture result into a
  capability claim.
- **`complete` is the most authorising-sounding member of its own vocabulary**, and the divergence
  between the contract meaning ("internally complete") and the English meaning ("done, nothing
  missing") is real. The mitigation in place is genuine but soft: the reviewer's own scope statement
  **travels with the artifact verbatim** (§8). What does not exist is a machine-checked precondition
  on any *consumer* — because **no consumer exists yet** (`G11`: nothing is persisted anywhere). The
  hazard is therefore **latent, and it goes live at the `ThesisVersion` persistence work order**
  (plan `:310-311`). That is the change that must add the check, and it should be written into that
  work order now rather than rediscovered.

**The rule:** when a pre-registered prediction is about a *class* of input, a run on a different class
neither confirms nor falsifies it — record **"untested"**, never "passed", and state the mechanical
reason the two classes cannot be silently conflated. This is the amendment un-enacted **L22** needs:
L22 covers the *null-result* case; this covers the *wrong-population* case.

**Evidence:** `docs/product/results-review-slice-report-2026-08-17.md` §1, §2, §4, §8 (on `e9ef53f`);
`finance-capability-matrix-2026-08-13.md` §6.

### L-cand-17.9 — A repeatedly-surfaced trivial action that never gets done is a ROUTING defect, not a diligence defect
The two dark-launch expiries (surfaces #1 portfolio brief and #4 paper-trade evaluator, both expiring
**2026-08-31**, decide by **2026-08-28**) were surfaced by **five consecutive `arbi-red-team` vets**
(2026-08-13 → 2026-08-17) and carried forward every single time. The action required was a **two-line
append** to `james-inbox.md` — I2, squarely inside standing authority, roughly sixty seconds. It was
deferred five times and finally landed as its own PR (`#120`) at the close.

**The honest answer to "what makes a repeatedly-surfaced trivial action not get done":**

- **A vet's output is a verdict on the mission in front of it.** Its *carried-forward* observations
  have no owner, no queue entry and no definition of done. **Being trivial is exactly what keeps it
  off the task graph**, because a task graph is built from the mission's deliverables — and a
  60-second doc append is never a deliverable of a code mission.
- **Re-surfacing felt like the system working.** It is not. Re-surfacing is *detection*; the row
  landing is *remediation*. Five detections with zero remediations is a control that measures itself
  as healthy while its output is discarded — structurally the same defect un-enacted **L20** names
  for a gate that asserts on a job's status instead of on the artifact.
- **It is not fixed by remembering harder.** The mechanical fix is cheap: **an observation carried
  forward by a vet must terminate in a durable row before the mission it was raised in can close** —
  the mission's close writes the row, or the vet's finding is not discharged.

**The tell, and it is a good one:** the row as filed says *"this row is **5 vets** overdue"* and
*"surfaced by **four** consecutive `arbi-red-team` vets (2026-08-13 → 2026-08-17)"* **in the same
sentence** (`james-inbox.md`, PR #120). The count of an undiscipline is itself undisciplined. Worth
correcting when #120 is merged; recorded here rather than fixed, because a dream does not mutate its
