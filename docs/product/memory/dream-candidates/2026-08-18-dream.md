### L-cand-18.2 — A fix is not safe because the defect it targets is real
`security-engineer` found **four genuine defects in the R1 fix itself**, on a fix whose target
defect was unambiguous (the job-failure banner could not fire on any day). Two of the four are worth
carrying by name because they are opposite failure shapes:

- **A blind spot the fix would have inherited.** A fixed one-day lookback covers nothing between
  Thursday's compose and Saturday midnight — the brief runs Sun–Thu (`daily-brief.yml`,
  `cron: "30 20 * * 0-4"`) — **a 27-hour hole every week**, which would have silently dropped
  **Friday's `backup_irreplaceable` failure**: the pg_dump protecting `theses`, `holding_lots` and
  the tax positions. Fixed by deriving the lower bound from the previous successful `compose_brief`
  and flooring it at seven days (`asxos/brief/compose.py`, `_job_failures` docstring at :670-699).
- **An egress path the fix *activated*.** `asxos/jobs/utils/fallback_email.py` was the only
  `job_runs.error_message` writer that did not redact, and that was **survivable solely because the
  broken filter could never match its row.** Widening the window makes that text email-reachable,
  and its recorded live failure shape carries a bearer token. Now
  `redact_secrets(...)[:1000]` at `:113-116` — **redaction precedes truncation**, because cutting
  first can split a credential across the 1000th character and leave an unrecognised prefix.

**The generalisable form, and it is the second half that is new:** repairing a broken control
**changes the threat model of everything downstream of it**, because the broken control was load
bearing as a *suppressor*. Anything that was safe only because the broken path never executed
becomes reachable at the moment of repair. So the review question is not "is this fix correct?" but
**"what was protected by this thing being broken?"** Both were fixed pre-merge in #132.

### L-cand-18.4 — "No writer anywhere" is a distinct failure class from "no data yet", and it routes to a different fixer
`disposed_at`, `tax_settings`, `screening_rules`, `thesis_evidence` — in each case **the judgement
could not have been recorded even if it had been made.** There is no path from a decision to a row.

> **Correction applied per L-cand-18.6.** `disposed_at` is verified in this worktree: **zero write
> sites** (see the box in L-cand-18.1). The other three are carried from session evidence and are
> **not** re-verified here — they are named as members of the class, not asserted with counts.

**Why the distinction is operationally load-bearing:**

| Diagnosis | What it means | Who it routes to |
|---|---|---|
| *No data yet* | The recording path exists; the decision was never taken | **a person** — make the call, run the job |
| *No writer anywhere* | The decision may well have been taken; nothing could ever have written it | **code** — build the write path |

Conflating them wastes a cycle in the most expensive direction: you go asking James to make a
decision he may already have made, and come back with the table still empty. **The probe that
separates them is one grep for a write site**, and it takes seconds — far cheaper than the round
trip it prevents.

I ran a **paraphrase** of a query against production, and only later ran the **literal string
