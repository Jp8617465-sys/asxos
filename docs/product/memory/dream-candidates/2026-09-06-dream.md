### L-cand-47 — Independent immutable-head verification is the autonomy substrate that worked

`proposed_target: approved-lessons.md`

The standing-lane design separates three facts that earlier prompts blurred:

1. a producer authored a branch;
2. an independent job executed the branch at a validated immutable SHA; and
3. a different least-privilege job opened the draft PR only if verification passed.

In `nightly-triage.yml`, the branch name and 40-hex remote SHA are validated at
`:156-173`; the verification job has only `contents: read`, checks out that SHA with
`persist-credentials: false`, confirms `HEAD == EXPECTED_SHA`, and runs the suite at
`:243-283`; the publisher re-reads the remote SHA before opening a draft at `:285-315`.
`backlog-roll.yml:220-258,264-335` generalises the same shape to a bounded matrix. The
security contract states the boundary directly: agent-authored code executes only in the
separate credential-free verification job
(`docs/product/security-perf-mission-loop.md:203-207`).

The merge train applied the same principle at its final gate: current CI had to belong to
the exact head being merged, and any new head required a fresh run. That allowed aggressive
remediation without confusing an old green result with current code.

**Lesson:** the scalable unit of trust is not “an agent says tests pass.” It is an immutable
commit whose declared contract is checked by a credential-free verifier, followed by a
state transition that revalidates the same SHA.

### L-cand-48 — Remove the branch credential from the model; do not merely teach the model to be careful with it

`proposed_target: a governance-doc PR→James`

The strongest current verification boundary stops one job too early. All three producer
agents still receive a repo write token to push their branch. GitHub Actions job permissions
are repository-scoped, not ref-scoped; the residual prompt-injection-to-push risk is openly
P1 and dispatch-gated (`security-perf-mission-loop.md:344-370`). This is why the workflows
remain owner-only manual dispatch despite standing I3/I4 authority.

**Proposed architecture:** make the model process tokenless.

```text
admitted Issue contract + immutable base SHA
                    ↓
tokenless agent workspace produces patch + manifest
                    ↓
credential-free verifier applies patch, runs gates, emits attestation
                    ↓
deterministic branch publisher (no model) validates:
  base/head lease · allowed paths · size · work identity · attestation
                    ↓
publisher alone creates claude/** branch and commit
                    ↓
read-only exact-head CI → PR publisher → draft PR
```

The publishing credential belongs only to deterministic code that cannot interpret Issue
prose or run agent-authored code. It accepts a bounded patch artifact, exact base SHA,
allowlisted paths, work/contract identity, and verifier attestation. It rejects symlinks,
submodules, protected paths, stale bases, unexpected binary files, oversized diffs, and any
manifest/patch mismatch. The agent never sees the credential, never invokes `git push`, and
cannot turn prompt injection into an arbitrary repository write.

The publisher must derive the changed paths and file modes from the patch rather than trust
the agent's manifest, and accept an attestation only when it is bound to the patch digest,
base SHA, workflow run, and named credential-free verifier job. It constructs the commit
without executing repository code. Otherwise an attacker could substitute a different
artifact between a clean verification and publication and the architecture would merely move
the confused-deputy boundary one job later.

This is the aggressive route to more autonomy because it makes capability mechanical. A
broader prompt grant around the existing producer token would preserve the P1 while hiding
it.

### L-cand-49 — Feature identity and contract revision must travel through git, CI, runtime, and observation

`proposed_target: a governance-doc PR→James`

The train was hard to reason about because campaign nodes, stage rows, click IDs, PR numbers,
branch bases, migration names, ledger rows, and handoffs all described overlapping units.
The existing ratified architecture already selects GitHub Issues and Projects as the work
substrate (`docs/product/architecture-decision-record.md:324-359`). The unmerged
chief-of-staff plan at `637d310` usefully makes the missing version-control rule concrete,
but remains advisory.

**Proposed durable convention:**

- one parent GitHub Issue is the feature/outcome identity;
- a sub-issue is one independently verifiable vertical slice;
- an append-only Issue comment is the admitted contract revision (`r1`, `r2`, ...);
- every branch starts from current `main` by default and names the parent/slice;
- every commit carries `Work-Item` and `Contract-Revision` trailers;
- every PR maps acceptance criteria to tests/evidence and states rollout, observation,
  rollback, and any reserved James action;
- the squash commit, final `main` SHA, workflow/runtime SHA, and observation all link back to
  the same identity;
- SemVer is reserved for a real public compatibility contract, not used to version plans.

**Lesson:** version control is not only source history. It is the causal spine from approved
intent to code to runtime evidence. A feature is not done because its PR merged; it is done
when its promised outcome was observed or honestly missed.

### L-cand-50 — Default every slice to `main`; deep stacks are an exception with a carrying cost

`proposed_target: approved-lessons.md`

The seven-PR product stack did permit parallel construction, but it also converted every
parent squash merge into restacking work and let four already-applied production migrations
remain absent from `main`. The 2026-09-03 handoff needed an explicit topology diagram and
warned that out-of-order merges forced rebases (`session-handoff-2026-09-03.md:40-55`).
Amendment I then needed special cascade and lease rules (`roadmap-state.md:494-532`).

**Lesson:** base one independently useful vertical slice on `main`. Stack only when the child
cannot compile or satisfy its contract without the parent. Default maximum stack depth is
two; any deeper stack records why the dependency cannot be represented as separate complete
slices. Maximum two active implementation PRs per feature keeps conflict and review state
bounded.

This is not a case for smaller ambition. It is a case for smaller integration batches so
agents can ship ambitious architecture continuously.

### L-cand-54 — Founder attention is an exception budget, not a step-by-step execution engine
