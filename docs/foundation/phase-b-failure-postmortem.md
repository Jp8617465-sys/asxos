# Phase B — Failure postmortem

Date: 2026-05-19. Subject: the existing ASX Portfolio OS in its current non-functioning state. Method: reading the commit history from 2026-04-01 to 2026-05-13, the `render.yaml` configuration, the FastAPI lifespan handler, the schema migration sequence, the CI workflows, and the env var distribution. The postmortem describes what broke and why; it does not editorialise about whether the previous architecture was sound.

## Proximate cause: the API claims healthy while every dependency is dead

The system reached a state by 2026-05-13 where the FastAPI process can start and respond to `GET /` with `"ASX Portfolio OS API is running ✅"` even though the asyncpg pool, the model cache, the Redis event bridge, the Redis Streams context refresh consumer, and the stock_universe view initialisation have all failed during the lifespan handler. Each failure was downgraded to `logger.warning(...)` at `app/main.py:165-300` and the process continued. `/health` does not probe these dependencies; it returns a static 200.

In parallel, the Render dashboard configuration had drifted from the checked-in `render.yaml`. Explicit comments at `render.yaml:421` and `render.yaml:440` admit that three crons (`news-ingestion`, `earnings-sync`, `semantic-maintenance`) were defined in YAML but never created on Render. Holdings news and earnings calendar have been stale since they were specified. The Render web service exists, but with stale environment variables — the commit `805c959a chore(infra): centralise DATABASE_URL in asx-db env group` on 2026-05-12 indicates the team was still in the middle of moving env vars to a shared `asx-db` group when work effectively stopped.

A separate credential rotation event triggered a circuit breaker in the connection pool. Per session memory: "Render DB auth failure (circuit breaker + wrong creds). Login code fix (username field + HttpOnly cookie). Commit f3668332." The commit `816011de chore(security): remove scripts containing old DB credentials` on 2026-05-06 confirms credentials had to be rotated. The new credentials propagated to some surfaces but not all crons; jobs that ran from a context not in the `asx-db` env group continued to fail with auth errors that surfaced as `logger.warning` messages rather than aborting the API.

The combined effect: from the outside, the system reports healthy. From the inside, every subsystem the user depends on is offline. No signals are being generated because Render crons that would invoke `generate_signals.py` either do not exist on the dashboard, run with the wrong env vars, or run against a database the API thinks it has a pool for but does not. The morning brief has not been sent. The user-facing endpoints return 500 because they cannot read from `signals` (the asyncpg pool is None) or load the active model from the cache (the warmup at `app/main.py:228-249` failed silently).

## Contributing factors: how the system was made fragile

**Graceful-degradation startup.** The single highest-cost design decision in the codebase. Six dependency init blocks at `app/main.py:165-300` are wrapped in `try/except: logger.warning(...)` and the process continues. The pattern is consistent across asyncpg pool (line 186), stock_universe view (line 225), model cache warmup (line 249), Redis bridge (line 262), Redis Streams + context consumer (line 286), and live price loop (line 299). The system was deliberately built to start even with dead dependencies. The reasoning was probably "don't let one bad component break the whole API," but the practical effect is that the API actively lies about its own state, and no outside observer can tell which component is broken without inspecting logs the user does not have a habit of reading.

**`render.yaml` as documentation rather than source of truth.** The lines 421 and 440 comments admit Render dashboard state diverged from YAML. The author who wrote those comments understood the divergence existed; it was acknowledged debt that never got closed. Render auto-deploys from GitHub by reading `render.yaml`, but services and crons are not auto-created — they must be created manually through the dashboard. This human step in the deployment pipeline was the drift entry point.

**Env var sprawl.** Approximately sixty distinct environment variables are required across `app/` and `jobs/`, distributed unevenly across the Render service and the various crons. Some crons inherit from the `asx-db` env group; others do not. `FRED_API_KEY` is declared for `macro-data` but not for jobs that incidentally call macro code. `VOYAGE_API_KEY` is declared for `semantic-maintenance` only. `ALERT_WEBHOOK_URL` and `ALERT_EMAIL` are referenced in code but missing from `render.yaml`. The migration to a centralised `asx-db` env group (commit 805c959a) was in progress and incomplete when the system stopped working.

**Feature flags left in a half-removed state.** Commit `f7e3f38c fix(auth): remove AUTH_FLOWS_ENABLED gate` removed an auth feature flag on 2026-05-12. The fact that an `AUTH_FLOWS_ENABLED` flag existed at all means the auth path had been gated, partially deployed, and left half-built. Two `ENABLE_*` flags survived the removal: `ENABLE_ADVISOR` at `app/main.py:160` and `ENABLE_LIVE_PRICES` at line 293. Both gate code paths to a non-fatal warning when missing inputs are detected. Each flag is a half-deployed feature that could leave the system in an unexpected state in production.

**Schema drift between code and database.** Five commits in May 2026 alone reference schema mismatches: `8110d8f3 fix(db): align repositories with current schema`, `fd4f87cb fix(db): align status CHECK constraints to allow full state machine`, `5175f5aa fix(db): remove expires_at from portfolio_repository INSERT (column never created)`, `de2eb165 fix(tax): SMSF franking refunds, Medicare levy in CGT, ... signals.price NUMERIC`, and the earlier `migrations/020` (which fixed an FK pointing at a nonexistent `users` table per Phase 1's audit). Each represents a divergence between what the code expected the database to look like and what was actually there. None of these were caught by CI — the test suite runs against an in-memory or migration-bootstrapped database, not the production Supabase.

**CI volume without CI rigour.** Six GitHub Actions workflows exist (`backend-ci.yml`, `ci.yml`, `e2e-auth-tests.yml`, `e2e-full.yml`, `frontend-ci.yml`, `v2-execution.yml`). The commit history shows repeated `fix(ci): unblocks CI` and `chore: auto-format ... unblocks CI` entries. CI was a blocker the team kept resolving rather than a source of confidence. None of the workflows verify Render dashboard state, env var completeness across services, or end-to-end pipeline health. They run unit tests, type checks, and lint — local correctness, not deployed correctness.

**Memory pressure in the feature pipeline.** Commits `911f6412 fix(jobs): batch technical feature computation by symbol to prevent OOM` and `179cb913 fix(jobs): stream-write feature batches to DB to eliminate OOM concat` on 2026-05-04 indicate the feature engine was running out of memory on Render Starter instances. 2,200 tickers times 22 features times 760 days of history exceeds what fits comfortably in a 512MB worker. The fixes are correct but the discovery happened in production, after months of running without anyone realising the OOM was imminent.

## Systemic causes: what about the workflow let this accumulate

**Sprint cadence outpacing consolidation.** The commit log shows S20 through S26 merged as a unit on 2026-05-06 (`d2d1bd22 feat(sprints): merge S20–S26 post-audit sprint sequence`). Seven sprints worth of work shipped in a single merge. Each sprint added features; no sprint was dedicated to retiring debt or verifying that the previously-shipped infrastructure still ran. The cadence was "produce, produce, produce" with no scheduled "stop and confirm everything still works" beats.

**SaaS-shaped architecture for a single-user system.** Authentication, password reset, RLS policies, subscription scaffolding, multi-tenant user_id columns, admin dashboards, AFSL/REP 798 compliance posture — all built into a system that has only ever had one user. Each was a source of complexity and breakage that contributed no value to the actual use case. The commit `b06b35bf chore: delete dead code — compliance_filter, goal_service, coach memories, MODEL_A_API jobs, wireframes, design-system pages` shows the team was finally deleting some of this on 2026-05-05, but by then the SaaS shape had calcified into the architecture.

**Bug-driven development as the steady state.** Of the most recent 30 commits, more than 20 start with `fix(*)`, `chore(security)`, `style:`, or `refactor:`. Only a handful are net-new functionality. The team was running to stay still — most weeks, the dominant work was "make the system as healthy as it was last week, plus a small increment." This is firefighting, not building, and it accelerates schema/code/infrastructure drift because no time is left for consolidation.

**No deployment verification step.** Husky pre-commit hooks ran `npm run type-check`, ESLint, Prettier, and Jest with 80% coverage. Push hooks ran the full Jest suite and `next build`. None of these verified that Render had received the right `render.yaml`, that env vars were complete on every cron, or that the production database matched the migration sequence. The team had local-correctness CI and deployed-correctness no-CI.

**Multiple improvement initiatives running in parallel without coordination.** In the first two weeks of May 2026, the team was simultaneously: removing the `AUTH_FLOWS_ENABLED` feature flag, centralising `DATABASE_URL` into the `asx-db` env group, fixing repository/schema alignment in five separate commits, removing scripts containing old DB credentials, executing the S20-S26 security sprint sequence, fixing tax math (the SMSF franking refunds commit `de2eb165`), and applying OOM fixes to feature computation. Any one of these is a legitimate improvement. Run six of them concurrently on a solo project with no consolidation pause and the interactions produce the state visible today: every individual improvement is sensible, the aggregate state is broken.

**Render dashboard requires human action that no checklist captures.** The drift between `render.yaml` and Render dashboard happened because creating a new cron is a manual step. The `render.yaml` is a description; the dashboard creates the actual services. The team had no checklist that said "after merging a `render.yaml` change, log into Render and verify the new services exist." The drift accumulated quietly.

## Lessons for the new repo: what must be encoded to prevent recurrence

1. **Hard-fail startup, no exceptions.** `app/main.py` lifespan in the new repo must `raise` on any dependency init failure. No `logger.warning(...)` and continue. The API does not start if the asyncpg pool fails, the active model is unloadable, the migration count drifts, or the EODHD key is absent. `/health` probes every dependency and returns 503 if any has failed. The build guide enforces this and the system-architect's Phase 4 spells out the lifespan code shape.

2. **MCP-driven service management, no dashboard clicks for routine changes.** The new system uses Render MCP and Supabase MCP for every routine operation. The `make check-drift` target uses the Render MCP to compare actual deployed services against `render.yaml` after every deploy and refuses to proceed if drift is detected. The rule is simple: never edit anything in the Render dashboard except for one-time account setup. Every change goes through `render.yaml` + `git push` + Claude Code reconciliation.

3. **No feature flags for half-deployed features.** A feature is either merged and live, or it is on a branch. The new repo does not have `ENABLE_*` env vars that gate code paths. If a feature is not ready, it does not merge. The build guide explicitly bans this pattern.

4. **No auth, no `user_id`, no RLS, no multi-tenancy.** The single largest source of debt-producing code in the old repo. The new repo has none of it. Single bearer token for the API, single Supabase project, no per-user filtering anywhere.

5. **Centralised, fail-fast env var loading.** `asxos/config.py` reads every required variable at startup via a single `Settings` class. Missing required vars cause the process to refuse to start. No `os.getenv` scattered through services. The build guide shows the exact shape.

6. **Smaller test suite, load-bearing tests only.** Approximately 400 tests, not 5,000. Each test must defend against a named failure class — schema migration safety, training/serving parity for the feature engine, tax math boundaries, signal threshold boundaries, EODHD ingestion idempotency, brief composition smoke. No snapshot tests, no tests that exist to inflate coverage.

7. **Consolidation sprints, not just feature sprints.** Every fourth or fifth milestone is purely "stop and verify." M6 is itself such a milestone — it does not add capability beyond what's needed to confirm the previous five worked. The principle scales beyond M1-M6: after every burst of three or four feature milestones, one milestone is dedicated to drift detection, log review, and tidying.

8. **Smaller stack, fewer moving parts.** Six jobs not 86. Ten tables not 122. One web service, one database, one storage backend (the DIY GitHub backup repo), one email provider, one monitoring deadman switch. Every external dependency is a potential drift surface; the fewer dependencies, the less drift.

9. **No "graceful warnings" anywhere in infrastructure code.** This is the broader version of lesson 1. If something cannot be reached, raise. If something is misconfigured, raise. The system makes its problems visible to the operator immediately; it does not absorb them.

10. **Spec-first for any non-trivial domain logic.** The tax math is the clearest example: rather than porting flawed code, we wrote `docs/spec/tax-alpha.md` and the implementation reads from it. Apply the same pattern to any other domain that has had bugs — signal thresholds, regime classification, screening rules. The spec gets reviewed by a human; the code follows.

The new repo's first commit lands with these lessons encoded. They are not aspirational; they are constraints on what the first M1 deliverable looks like. If any of them is violated in M1, M1 is not done.
